Agent Screen / Virtual display architecture

How an AI agent virtual display works on macOS.

Giving an AI agent a Mac screen without taking over your own requires solving four macOS problems: creating virtual displays, delivering background input without warping the cursor, attributing new windows, and keeping ColorSync from stuttering.

Written in Rust Open Architecture Decision Records in docs/adr/

Virtual display vs built-in computer use vs VM

Every way to let an AI agent drive GUI apps on a Mac trades off convenience, concurrency, and isolation differently. Pick the one that matches the risk and workflow of your task.

Criterion Agent Screen Built-in computer use macOS VM / cloud desktop
You keep your mouse and keyboard Yes, agent works on a virtual display No, drives your real pointer Yes, inside the VM window
Uses your real Mac apps and logins Yes, nothing to reinstall Yes No, set up apps and accounts per VM
Several agents working at once Yes, one display per session (up to 4 each) No, one shared cursor One VM per agent (high RAM and disk cost)
Human takeover for logins or captchas Menu bar Peek and one-click Takeover Watch your own screen Open the VM window
Security isolation from your Mac No (drives your real apps) No Yes, full OS boundary
API stability / distribution Private macOS APIs, notarized DMG / Homebrew Vendor-supported, no install Public virtualization frameworks

When to choose a VM instead: if you are running untrusted code, need OS-level sandboxing, or need Linux or Windows apps. When to choose Agent Screen: when you want Claude Code, Codex, or another MCP agent to work with the macOS apps, local dev servers, and accounts already on your Mac without interrupting your own work.

Background input through SkyLight and Accessibility

Creating a virtual monitor with Apple's private CGVirtualDisplay API is only half the problem. Sending clicks with public cursor-warping APIs still moves your real mouse pointer onto the virtual display and activates the target app.

Agent Screen delivers clicks and keystrokes straight to the target application process using SkyLight's private SLEventPostToPid along with a focus-without-raise handshake (ported from trycua/cua, MIT). Because no real cursor warp occurs, your pointer and active window stay put (ADR 0001).

Alongside coordinate input, agents can inspect a window's macOS Accessibility tree (get_window_state) and press buttons, choose menu items, step sliders, or write text fields by numbered element (act_on_element). Because those actions address controls by identity rather than pixel location, a button press still lands if the window moved or resized.

When macOS does not permit a background route, such as dragging a file from Finder into a browser or triggering certain Electron menu shortcuts, Agent Screen places the operation in the visible Input Queue. A card shows the exact path or click point on the display preview, and nothing touches your pointer until you press Allow.

Deciding which windows belong to the agent

An app started by an agent stays running after launch_app returns, and you might open a window in the same app yourself. Agent Screen hooks AXWindowCreated notifications to place each new window accurately (ADR 0007):

  • A new window of an app the agent started moves to the agent's display if that display was driven in the last 3 seconds (30 seconds during cold start) and you did not click or type in that app, Finder, the Dock, or a launcher meanwhile.
  • A window you open stays on your screen. If an agent opens a new window in an app that is already running, it may briefly flash on your screen for about 30 ms (140 ms at most in tests) before moving.
  • Windows you hand over to an agent always remember where they came from and return to your screen when the agent ends its display or disconnects (ADR 0004).
  • If you use AeroSpace, Agent Screen ignores AeroSpace's closet display everywhere (docs/aerospace.md).

Preventing macOS ColorSync stutter with many displays

Every time a virtual display connects or disconnects, macOS WindowServer asks colorsync.displayservices for every online display's color profile with a 50 ms deadline, retrying every 5 seconds when late. Internally, colorsyncd parses /Library/Caches/ColorSync/com.apple.colorsync.devices five times per online display, and macOS keeps a record for every display ever seen, storing display names in 39 languages.

On a test Mac documented in ADR 0009, 84 historical records with 4 displays online took 66 to 91 ms per read, triggering hundreds of retry loops per minute and making the Mac stutter. Agent Screen includes an optional Smooth Display Changes helper (AgentScreen colorsync setup) that removes offline factory-only records and trims display names to English and your preferred languages, preserving any custom color profiles. With the helper enabled on the same Mac, 13 displays online read in 23 ms.

Honest trade-offs and limits

All code, architecture decision records, and test scripts are public in github.com/Fanzzzd/agent-screen under the MIT license.

  • macOS 15+ and private APIs: Relies on SkyLight and CGVirtualDisplay. Cannot ship on the Mac App Store, and future macOS updates could require patches.
  • Copy, paste, and undo shortcuts: Require a focused app on macOS, so agents read and insert text via Accessibility instead.
  • Canvas apps and games: Apps that ignore per-process events may not respond to background clicks.
  • Locked screen: macOS blocks screenshots and input on all displays while the screen is locked.
  • Viewer scaling: The live Viewer scales the display at one pixel per point, so small text can look soft in the preview window; agents' own screenshots are unaffected.
