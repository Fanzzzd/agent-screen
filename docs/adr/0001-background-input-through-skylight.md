# Input reaches agent windows through SkyLight, not the real cursor

Agent Sessions and the Viewer deliver clicks and keys to windows on an Agent Display by posting events straight to the owning process with SkyLight's private `SLEventPostToPid`, plus a focus-without-raise handshake (recipe from trycua/cua, MIT). The obvious alternative, warping the real cursor onto the virtual display and clicking there, is public API and works with every app, but it takes the mouse and keyboard away from the user, which is the problem Agent Screen exists to solve.

[ADR 0013](0013-user-approved-input-queue.md) records the accepted exception for operations that cannot run in the background: a visible, user-approved Input Queue shared by sessions. Background routes remain first. Complete drags without one can run with the real pointer only after the user allows them, under the visible grant in ADR 0013. A menu item of an Electron app can be chosen the same way, with a real click on the Agent Display's menu bar, since Electron takes an accessibility press for the item's shortcut (#39). A click an app took only partway in the background can be repeated with the real pointer the same way, when the agent asks with `real_input: true` (#134).

## Consequences

- Only apps that accept per-process events work. Canvas apps and games that filter them need a brief foreground activation instead.
- The first click on an inactive window only activates it, as with a real click.
- In an app the user also uses, keys posted to the app reach its key window, which can be the user's window on their own screen. The focus record alone doesn't take key focus from another window of an app in the background. A click on an empty spot of the agent's title bar does, and so does setting the agent's window AXMain, with the app still in the background. Before any key goes out, Accessibility must report the app's focused window as the agent's or on an Agent Display. Otherwise the call fails, names that window and sends nothing (#120, `agent_screen_model::key_window`).
- A macOS update can break the private symbols. Every call falls back to the public `CGEventPostToPid`, which reaches fewer apps.
- An app on an Agent Display can still bring itself to the front, as Electron does to show a window. When the agent started the app and the user didn't just act on it, Agent Screen gives the front back to the user's app as soon as macOS reports the change, a few ms later (issue #67). The ime path (ADR 0008) holds the front on purpose and is left alone.
- An app can be the user's front app while one of its windows is on an Agent Display, as a browser the user works in while the agent works in another of its windows (#110). Posted keys reach that app's key window, the user's, and the focus record is refused there, since telling the front app its window lost focus ends the user's input method session. A posted click on the agent's window would make it key and take the user's typing. So nothing is posted to that app while another of its windows is focused. A single left click presses the control under it through accessibility, or picks the text field there. Text goes into the picked field by setting its value, then reads back. Return, Escape, Backspace and Command-A become the picked element's confirm, press and cancel actions, or edits of its value. Tab and Shift-Tab set AXFocused on the next or previous element of the agent's page whose focus can be set, in accessibility tree order; the app's focused window stays the user's. Return in a Chromium text field has no route: Chromium publishes no confirm action for it, and nothing that tells a form's submit button from its other buttons, so the error names the form's buttons. Everything else fails and names the focused window (`agent_screen_model::shared_app`). Pages see no key events for that text, and the field isn't focused. A focused window on the agent's own display, the one its target is on, isn't the user's: a Handover there or another window of the agent's. That holds only while the app has no window on the user's screen; with one, the user may click it while a long `type` is still sending keys, so the focused window counts as theirs. Input goes as when the agent's window has focus. WeCom, with its only window handed over, was the user's front app, and every click and key was refused as reaching that Handover (#162).
