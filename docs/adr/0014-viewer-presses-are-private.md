# The Viewer's presses are private

Accepted, 2026-11-12.

A press the user makes in the Viewer is a real mouse event. WindowServer routes it to Agent Screen, and it also reaches every other app's NSEvent global monitor as a press outside that app. Qt closes a pop-up on such a press while its parent isn't active (qtbase 5.15, `qcocoawindow.mm`, "Close popup when clicking outside it"). An app on an Agent Display is never active. So when the user clicked a contact in WeCom's search results through the Viewer, the list closed before Agent Screen hit-tested the click, and the click went to the chat row under the list.

Agent Screen takes those presses before WindowServer routes them. An active HID event tap, inserted after the input observer of ADR 0013 so it runs first, takes a press only where the Viewer's picture is under the pointer with no visible window over it. It drops the original and hands the press to the Viewer's handler on the main thread. The drags and the release of a press it took go the same way, wherever the pointer goes meanwhile. Every other event passes unchanged: presses on the Viewer's header, on any other window, on a blocked Viewer, and all keys, moves and scrolls. Input Agent Screen posts for an Input Loan carries ADR 0013's tag and passes too.

The tap runs on its own thread. It decides from the picture the Viewer publishes on each layout and one window list call, so no mouse event on the Mac waits for Agent Screen's main thread. An active tap delays every mouse event by its callback; a callback on the main thread would delay all of them whenever that thread is busy. A key typed right after a press the tap took waits on the tap's thread, at most 100 ms, until the main thread has handled that press: handling it makes Agent Screen the front process, and the key must reach the Viewer, not the app that was in front before.

Three cases keep AppKit's behavior. While a menu is open on the user's screens, a press passes: the menu closes on it and takes it, as it would anywhere. A menu on an Agent Display, shown in the Viewer, doesn't count, so the user can pick its items. While Agent Screen runs a modal panel or alert, the handler drops the press, as AppKit drops presses outside a modal window. When the handler lets a press go, the Viewer's window gets it as AppKit would have sent it.

The press stays the user's. The main thread tells the input observer of ADR 0013 about each press the tap takes, so a press in the Viewer still revokes an Input Grant. It reports the press to the monitors Peek and Handover by drag read. ADR 0013's observer stays listen-only. The tap suppresses no input the user aimed elsewhere, so this doesn't revive the input suppression ADR 0001 and ADR 0013 rule out.

If macOS disables the tap for a slow callback, Agent Screen enables it again and forgets the presses it held, as their releases went by unseen. If the tap can't be made, presses reach other apps as before, and a Qt pop-up on the display closes on them. `AGENTSCREEN_NO_PRIVATE_PRESS=1` leaves the tap out, to tell a problem it causes from one it fixes. `debugViewer` reports `privatePress`. The e2e `viewerpopup` clicks a list that closes on any press in another app, as Qt's does, with the real pointer, and clicks the picture while a menu is open.

A borderless window has no title bar, so Agent Screen never clicks its top edge to wake it before input, as opening the Viewer does, or drags it there as a title bar: a window counts as titled only with a close, minimize, zoom or full screen button. Waking the list that way picked its first item. The first window of an app just started and a file panel still get a click on their top edge when they have no empty title bar: they drop their first click otherwise, and a frameless app window's top edge is usually its drag area.

A private press still made Agent Screen the front process before the press went out, as ADR 0008 and issue #41 need, and with 0.1.32 WeCom's results still closed before the click arrived. Making the Viewer key activates Agent Screen, and taking the front makes the app on the display lose active if it had it. WeCom's list holds the keys once the agent types into it, and a list that closes as its app or window loses active is gone by the time Agent Screen hit-tests the press. So a press on a list or panel reaches it first. A press counts as one when the window under it floats above the normal layer, or lies over another window of its own app there (`viewer_press`). For such a press the Viewer becomes key, and Agent Screen the front process, once the release is delivered. Keys typed meanwhile wait, at most 100 ms each, as after any press. Every other press keeps ADR 0008's order. A press on a list of the front app also leaves the keyboard focus where it is, as a real click on it would: focusing the list took key from its window, and a list that closes then closed. The e2e `viewerqt` clicks results in a real Qt app (PySide6), in Qt's pop-up, in a borderless window that takes the keys and in one that never does, with the user's app in front and with the list's app in front.
