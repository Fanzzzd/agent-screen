# A new window is the agent's when the agent just acted and the user didn't

An app the agent started keeps running after `launch_app` returns. The user may use it too, so Agent Screen has to decide, for each new window the app makes, whether it goes to the agent's display. A catch on the app's AXWindowCreated notification decides as the window appears. Deciding later shows the window on the user's screen, and AeroSpace lays out the user's workspace around it.

The catch takes the window when the display was driven in the last 3 s and the user didn't act on the app meanwhile.

- **The display was driven.** The agent's input, element actions and launches on the display count, and so does the user's input through the display's Viewer. A cold start counts for 30 s, for that app alone: every window it makes in that time is the agent's unless the user acted on it. A slow app may take that long to show its first window, and one restoring a session shows several.
- **The user acted.** A key press to the app, or a click on one of its windows. A key press or click in Finder, the Dock or a launcher such as Spotlight, Raycast or Alfred counts for every app, since those open files and apps. A key press counts for the app with keyboard focus, which Accessibility reports: a launcher panel takes keys without coming to the front. The last 3 s of presses count, not only the latest. Global NSEvent monitors report these. Events Agent Screen posts to a pid don't reach those monitors. They do reset the HID idle timer, so that timer can't tell the two apart.

When only the user acted, the window is theirs, and nothing moves it later. When both acted, or neither did, the window stays where it opened, and the agent can move it with `place_window` from `list_windows` with `strays: true`. The agent's next screenshot or window state names it, and the launch poll leaves it alone. Taking back any window of the app makes all its windows the user's. A new window such an app opens on the display by itself, beside a window of its own still there, goes back to the screen the taken-back window came from, unless the agent acted there in the last 3 s and the user didn't. A Handover of the app ends this. A new window of an app the user handed over, which the agent didn't start, follows the same rule; when one stays on the user's screen, the agent is told to ask for a handover, since `place_window` takes only its own apps' windows.

A launcher is the exception, for any app, not only the agent's. Spotlight, Raycast and Alfred take keys in a panel that doesn't come to the front, so the front app while the user types there is the one they used last. When that is Agent Screen, they were working in a Viewer, and the app they open there belongs on the Viewer's display (issue #42): the first new window in the 10 s after their last key in the launcher goes to that display as a Handover, and so do the windows its app makes in the 2 s after. When the front app is another, they last clicked on their own screen, and the app opens there as before. Take Back Window returns such a window.

A window this rule leaves with the user stays theirs, but the agent can ask for it. `place_window` takes a window id or an app's name, and for a window of anyone but the agent's own apps it opens a Window Request: a card under the menu bar icon and a notification say which window, and the user answers Hand Over or Keep. The call waits for the answer, up to 120 s by default, and a window given goes over as a Handover. This covers the windows the rule can't attribute. An app the agent started with a shell command such as `open -a` comes through LaunchServices, whose parent is launchd, so nothing ties its window to the agent. An agent that couldn't place such a window quit the app, and the user's VM in it, to start it again through `launch_app`. Taking a user's window without asking stays ruled out: from the window alone, Agent Screen can't tell it from one the user is working in.

We tried two rules before this one. Under the first, the catch left alone any window the app made while it was frontmost. That left the agent's own windows on the user's screen whenever the app came to the front. Under the second, any window within 3 s of an agent action went to the agent. That took windows the user opened while the agent worked, and it marked a slow agent window as the user's for good.

The rule still guesses wrong when the user clicks a link in another app within 3 s of an agent action and the link opens in a browser the agent started. That window goes to the agent's display, and the user takes it back with Windows ▸ Take Back Window.
