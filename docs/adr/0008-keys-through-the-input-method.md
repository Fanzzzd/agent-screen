# Keys through the input method borrow the user's keyboard, on request

ADR 0001 posts keys to the target process and keeps it in the background. An input method (pinyin, Japanese, Korean) composes only for the app with keyboard focus, so it never sees those keys. An Agent Session that has to reproduce an input-method bug, such as composition breaking on blur, can't do it with `type`, which inserts finished text.

`type` and `key` take `via_input_method`. With it, Agent Screen gives the target app keyboard focus for the call, posts the keys at the session level as a keyboard would, then gives focus back to the app the user had in front. `input_source` names a source to use for the call; the user's comes back after. `type` turns the text into the keys a US keyboard presses for it, so the agent types the letters the input method composes from.

This breaks ADR 0001's rule on purpose. For the call, the user's keys reach the agent's app and the agent's keys reach whichever app has focus. So:

- The agent asks for it on each call. Nothing turns it on for a session.
- It runs only when the user hasn't touched the keyboard or pointer for 2 s, and stops at the next touch.
- It runs only when the target app has keyboard focus, checked before every key. A modal system prompt, such as a keychain password request, keeps focus; Agent Screen then sends nothing. It also refuses while secure input is on, which a password field turns on.
- It takes at most 250 keys, about 10 s, a call.
- The Viewer and Peek say the agent is using the user's keyboard while it lasts.

We tried a session-level post without the focus check while a keychain prompt was in front. The keys went into its password field. The checks above came from that.

A Takeover doesn't cover this case: the user's input method composes in the Viewer, and Agent Screen passes the target only what it composed. With an input method selected, every key without Command or Control goes through the Viewer's input context. A key the input method passes through unchanged, inserting exactly the key's own characters with nothing marked, or doing nothing the Viewer sees, as for an arrow, Return, Delete or Escape, goes to the target as the original key, keycode and all; a game, a VM or a page's single-letter shortcuts get their keys. Only text the input method composed goes as Unicode text. A key the input method follows with its command, as Korean input commits a syllable and then asks for Return, Tab or an arrow, sends the text and then the original key; Pinyin's Return, which commits the letters as typed, asks for none. A password field, or secure input anywhere, skips the input context: composing there would show the password in the Viewer. Whether the focus is one is read through accessibility on a thread of its own, after anything that may move the focus: a click, Tab, Return, Enter, a shortcut, a commit that ends the composition, or showing the display. Arrows and a held key's repeats don't. An app may move its focus some time after the key, as Chrome's renderer does, so a look settles the focus only when the focused element changed from the one before, or when a second look agrees, a password field included. The second look runs 40 ms after the first and 100 ms after the key at the soonest. Secure input still on after a click or such a key waits for that lookup too, as the app that turned it on turns it off only once it handled the click or key; it then counts as a password field if it is still on. A failed or timed-out accessibility call settles nothing, and a Chromium or Electron app is asked to publish its page before its first lookup; until its page is up, which takes up to 3 s, only a field or a password field it reports counts. Until the focus settles, keys the input method would see, and Shift or Caps Lock, which switch its mode, wait, in order, and every key event after them waits behind them; the main thread never blocks. The answer routes them, so pinyin's first letter typed at once after a click composes, and a password field reached by Tab or focused by a page gets every letter as a key. If no answer comes within 400 ms, they go as keys, the safe choice for a password field. While text is marked, keys never wait: the composition already shows the focus is no password field. A click sends the keys still waiting before it, the same way. A lookup that finds a password field while text is marked drops the composition, uncommitted, and sends the keys that made it to the field as keys, so no letter is lost. A Takeover's end and a display switch drop waiting keys with the composition, and release every key the target got the press of, and the modifiers, so none stays down. Each key's release goes the way its press went. With a keyboard layout, keys go to the target as before. `agent_screen_model::viewer_keys` holds the rules.

A composition belongs to one generation, which a dropped composition, a Takeover's start or end and a display switch each end. The Takeover's end drops it at once, before any card or window can take the keyboard, and the input context discards its marked text; text an input method commits later belongs to no composition of the current generation and is dropped. A click on the picture, or the Viewer giving up the keyboard for another reason, commits the composition, as a native field does. An input method's correction of text already sent is left out, since sending it would type the text twice. The monitor once sent every key to the target, so the input method never saw one and the user could type only letters (issue #117).
