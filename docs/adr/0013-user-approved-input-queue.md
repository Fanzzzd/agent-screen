# Real input needs a user-approved queue shared by Agent Sessions

Accepted design, 2026-10-30. The queue, approval UI and a macOS executor for complete drags are implemented, and one for clicks on Electron menu items (see Menu items of Electron apps). `approved` means allowed; `completed` means the executor sent the complete drag and released its inputs. Generic `input_queue request` calls contain no executable action, and split presses cannot hold the user's button across calls. Real-keyboard operations are not routed through this executor.

ADR 0001 keeps input in the background. Some apps read the session's mouse-button state rather than the events sent to their process, so posting a drag cannot make it work. A private DevTools pipe handles this for apps Agent Screen starts, but not the user's existing browser. The user rejected an extension and does not want separate logins as the workaround. Background app capabilities and accessibility remain the first choices. When those cannot perform an operation, the user can explicitly lend real input under the rules below.

## Permission and scheduling

One Input Queue in the app serves every connected Agent Session. Only explicit user approval opens an Input Grant. It admits requests already waiting and new requests that arrive during the grant. The agent cannot grant itself permission. The approval card lists the sessions, displays and reasons. Allow Queue starts the grant; Not Now declines the waiting batch. A system notification accompanies the card. A batch the user allowed is not asked about again when its grant ends with nothing run; a new request or a revocation asks again. Its agents are told the approval lapsed, so they do not wait for a card that will not come.

Each complete operation is one Input Loan. Eligible requests execute FIFO, with at most one loan active. A held-button sequence is one operation from press through release. Screenshot capture and model reasoning do not occupy the loan. The platform must release the outgoing operation's held inputs before starting another, including after cancellation. A display in Takeover cannot execute a loan. No loan ends a Takeover or grants access to a new window.

A grant has no fixed duration limit. It ends after 30 seconds with no eligible operation waiting or running, or sooner when no operation is waiting or running and every participant declares itself done. A declaration affects only that session. New work from a participant clears its done declaration. A disconnected session or ended display loses its requests and active loan. Other sessions may continue under the existing grant after cleanup. Waiting for approval returns after 60 seconds without withdrawing the request; subsequent waits or retries refer to the same operation rather than submitting it again. A retry finds the newest request with the operation's token, so a declined or completed result stands. Only a token whose newest request the same session replaced or withdrew starts a fresh request, and the old request keeps its stopped result for any call still waiting on it. One session holds at most 64 requests, finished ones included, so it cannot fill the queue's 256 for the others; declaring itself done releases them.

## Revocation and restoration

Physical mouse or keyboard input immediately revokes the entire grant. The active loan stops; other requests stay queued for a new approval. Input generation must check revocation before each event. Cancellation does not free the execution slot until held inputs have been released. Agent-generated events must be distinguishable from physical input without suppressing or replaying the user's events.

The pointer position and front app/window are saved once at grant start, not between loans. Normal grant completion releases held inputs and restores that saved state. When the user revokes, release agent-held inputs but do not warp the pointer or activate a window: doing so would override the user's new action. The pointer may be on the Agent Display then, where the user can't see it; the guard that keeps the cursor off Agent Displays brings it back to where it last was on their screens, as it does at any other time. Cleanup releases only input held by the agent, never a newly pressed physical key or button.

The permission changes input delivery, not window access. Points must remain inside the owning Agent Display and target an authorized window. Foreground, target geometry, ownership, Takeover and secure-input checks apply before delivery, not just when the request is queued. System prompts and unexpected focus changes stop delivery. Global shortcuts and system menus are not covered. Other sessions' background input into the same process and the existing Keyboard Borrow must not overlap the loan.

A loan brings its window forward with Accessibility writes only: the window becomes its app's main window and the app becomes frontmost, with no app activation, which can make a window manager bring the app onto the user's workspace. AeroSpace still refreshes when the app becomes frontmost, and that refresh lays out the user's workspaces before it reads the claim file (ADR 0006). An app it has never seen in front, such as an accessory app, gets its focused window filed in the user's focused workspace, laid out on their screen and only then let go of as claimed, so the window stayed on the user's screen and containment stopped the drag (issue #121). So while AeroSpace runs, the loan rewrites the claim file every 10 ms for 0.5 s after the writes: each rewrite starts a refresh that reads the claims first and replaces the one for the activation. Nothing is pressed until the window has kept its frame for 0.3 s; if it moved all the same, it goes back first, and AeroSpace leaves the claimed window alone from then on.

## Presentation and routing

During the whole grant, each user screen has a thin click-through red edge that lies wholly on its glass, its outer side on the glass's edge. On a 14- or 16-inch MacBook Pro it follows the shape fitted to Apple's bezel art: continuous top corners, square bottom corners and the camera notch. Other screens get a rectangle, cut around a notch where NSScreen reports one: macOS gives no corner shape, and a guessed rounding larger than the real one would run off the glass's edge. A status bar at the bottom centre of the screen with the menu bar icon shows whether an action runs, the instruction to move the mouse or press a key to take control back, and the elapsed grant time; it stays clear of the card, never takes focus, and its Stop revokes the grant. The card shows the current task, a live thumbnail and the same instruction. The indicator stays visible during the idle grace period. Failure to show the indicator prevents real input.

Agents keep using the ordinary action tools. App-provided operations, the DevTools pipe and accessibility precede real input. An accessibility substitution must preserve the action's meaning; a point on a slider is not enough to infer a value without its range, orientation and geometry. Read back the result when the control exposes one. Known unsupported background operations enter the queue automatically. If an apparently successful background operation had no effect, the agent can retry with `real_input: true`. The result identifies the route used. Other input conflicts may use the same queue after their routing and containment are verified; approval does not switch every action to real input.

This is an explicit exception to ADR 0001. It does not revive hidden mouse-button latches, cursor time-sharing, input suppression or decoy cursors. Input monitoring uses a listen-only HID event tap and never suppresses or replaces the user's events. A missing or disabled observer prevents execution. The user knowingly stops using their input during a visible grant and can reclaim it at any time.

## Menu items of Electron apps

Amended 2026-11-04 for issue #39, with the user's explicit approval. Electron passes `[NSApp currentEvent]` to a menu item's click handler and reports anything but a mouse click as the item's keyboard shortcut (`triggeredByAccelerator`). AppKit runs an accessibility press with no current event, so every AXPress on an Electron menu item arrives as a shortcut. Apps that drop shortcuts while a text field has focus ignore it. A mouse event posted before the press doesn't become the current event; only menu tracking makes one, and tracking follows the real pointer. So a press on such an item can use the Input Queue.

- Scope: `press` on an enabled item of an Electron app's own menu bar, reached from a menu bar title. The Apple menu, context and pop-up menus, status items and other apps' menus keep accessibility. The press takes the queue by default only while the app's focused element takes text; `real_input: true` asks for it anyway and `real_input: false` sends the accessibility press, which arrives as the shortcut.
- The loan brings the agent's window forward as a drag's does. Then the Agent Display's own menu bar shows the app's menus: accessibility places the titles there. The pointer moves to the title on that display and waits up to a second for the screen to show that app's title there, which also covers a menu bar that hides until the pointer reaches it. Without one, as when Displays have separate Spaces is off, nothing is clicked. The menu the click opens must lie wholly on the Agent Display, or it closes and the loan stops. The pointer then reaches the item, across first into a submenu, and clicks it.
- Before every event the loan checks the grant, the user's touch, secure input, the display's frame, the app still in front and the menu still open. On any stop, a menu the loan opened closes with AXCancel. No key is sent, Escape included.
- While a request for the item waits or runs, the item is not pressed through accessibility: it would run twice. A declined or lapsed request returns `input_pending` and nothing else happens. A result the call has read is cleared, so pressing the same item again is a new request.
- When the loan has run and the session has nothing else waiting, the session is done, so the grant ends at once and the pointer and front app come back.
