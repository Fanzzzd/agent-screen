# Real input needs a user-approved queue shared by Agent Sessions

Accepted design, 2026-10-30. The queue, approval UI and a macOS executor for complete drags are implemented, one for clicks on Electron menu items (see Menu items of Electron apps), and one for complete clicks (see Clicks). `approved` means allowed; `completed` means the executor sent the complete operation and released its inputs. Generic `input_queue request` calls contain no executable action, and split presses cannot hold the user's button across calls. Real-keyboard operations are not routed through this executor.

ADR 0001 keeps input in the background. Some apps read the session's mouse-button state rather than the events sent to their process, so posting a drag cannot make it work. A private DevTools pipe handles this for apps Agent Screen starts, but not the user's existing browser. The user rejected an extension and does not want separate logins as the workaround. Background app capabilities and accessibility remain the first choices. When those cannot perform an operation, the user can explicitly lend real input under the rules below.

## Permission and scheduling

One Input Queue in the app serves every connected Agent Session. Only explicit user approval opens an Input Grant. It admits requests already waiting and new requests that arrive during the grant. The agent cannot grant itself permission. The approval card names the asking agent, draws each drag's path or click's point on its display's picture and lists the requests when there are several. Allow starts the grant; Not Now declines the waiting batch. A system notification accompanies the card. A batch the user allowed is not asked about again when its grant ends with nothing run; a new request or a revocation asks again. Its agents are told the approval lapsed, so they do not wait for a card that will not come.

Each complete operation is one Input Loan. Eligible requests execute FIFO, with at most one loan active. A held-button sequence is one operation from press through release. Screenshot capture and model reasoning do not occupy the loan. The platform must release the outgoing operation's held inputs before starting another, including after cancellation. A display in Takeover cannot execute a loan. No loan ends a Takeover or grants access to a new window.

A grant has no fixed duration limit. It ends after 30 seconds with no eligible operation waiting or running, or sooner when no operation is waiting or running and every participant declares itself done. A declaration affects only that session. New work from a participant clears its done declaration. A disconnected session or ended display loses its requests and active loan. Other sessions may continue under the existing grant after cleanup. Waiting for approval returns after 60 seconds without withdrawing the request; subsequent waits or retries refer to the same operation rather than submitting it again. A retry finds the newest request with the operation's token, so a declined or completed result stands. Only a token whose newest request the same session replaced or withdrew starts a fresh request, and the old request keeps its stopped result for any call still waiting on it. One session holds at most 64 requests, finished ones included, so it cannot fill the queue's 256 for the others; declaring itself done releases them.

## Revocation and restoration

Physical mouse or keyboard input immediately revokes the entire grant. The active loan stops; other requests stay queued for a new approval. Input generation must check revocation before each event. Cancellation does not free the execution slot until held inputs have been released. Agent-generated events must be distinguishable from physical input without suppressing or replaying the user's events.

The pointer position and front app/window are saved once at grant start, not between loans. Normal grant completion releases held inputs and restores that saved state. When the user revokes, release agent-held inputs but do not warp the pointer or activate a window: doing so would override the user's new action. The pointer may be on the Agent Display then, where the user can't see it; the guard that keeps the cursor off Agent Displays brings it back to where it last was on their screens, as it does at any other time. Cleanup releases only input held by the agent, never a newly pressed physical key or button.

The permission changes input delivery, not window access. Points must remain inside the owning Agent Display and target an authorized window. Foreground, target geometry, ownership, Takeover and secure-input checks apply before delivery, not just when the request is queued. System prompts and unexpected focus changes stop delivery. Global shortcuts and system menus are not covered. Other sessions' background input into the same process and the existing Keyboard Borrow must not overlap the loan.

A loan brings its window forward with Accessibility writes only: the window becomes its app's main window and the app becomes frontmost, with no app activation, which can make a window manager bring the app onto the user's workspace. AeroSpace still refreshes when the app becomes frontmost, and that refresh lays out the user's workspaces before it reads the claim file (ADR 0006). An app it has never seen in front, such as an accessory app, gets its focused window filed in the user's focused workspace, laid out on their screen and only then let go of as claimed, so the window stayed on the user's screen and containment stopped the drag (issue #121). So while AeroSpace runs, the loan rewrites the claim file every 10 ms for 0.5 s after the writes: each rewrite starts a refresh that reads the claims first and replaces the one for the activation. Nothing is pressed until the window has kept its frame for 0.3 s; if it moved all the same, it goes back first, and AeroSpace leaves the claimed window alone from then on.

## Presentation and routing

During the whole grant, each user screen has a thin click-through red edge that lies wholly on its glass, its outer side on the glass's edge. On a 14- or 16-inch MacBook Pro it follows the shape fitted to Apple's bezel art: smoothed top corners, square bottom corners and the camera notch, fitted so the line never runs past the art's glass. Other screens get a rectangle, cut around a notch where NSScreen reports one: macOS gives no corner shape, and a guessed rounding larger than the real one would run off the glass's edge. A status pill at the bottom centre of the screen with the menu bar icon names the agent using the mouse with the instruction to move it to take control back, or while nothing runs, the idle time before the grant ends; it stays clear of the card, never takes focus, and its Stop revokes the grant. The card shows the current step, a live thumbnail with the step drawn on it, and the instruction to move the mouse or press a key. The indicator stays visible during the idle grace period. Failure to show the indicator prevents real input.

Agents keep using the ordinary action tools. App-provided operations, the DevTools pipe and accessibility precede real input. An accessibility substitution must preserve the action's meaning; a point on a slider is not enough to infer a value without its range, orientation and geometry. Read back the result when the control exposes one. Known unsupported background operations enter the queue automatically. If an apparently successful background operation had no effect, the agent can retry with `real_input: true`. The result identifies the route used. Other input conflicts may use the same queue after their routing and containment are verified; approval does not switch every action to real input.

This is an explicit exception to ADR 0001. It does not revive hidden mouse-button latches, cursor time-sharing, input suppression or decoy cursors. Input monitoring uses a listen-only HID event tap and never suppresses or replaces the user's events. A missing or disabled observer prevents execution. If macOS disables the observer, the current grant is revoked. Only after its loan and cleanup have finished does the app re-enable the retained event tap and verify that macOS reports it enabled. Recovery restores observation, not the old grant: queued requests still need a fresh Allow. The user knowingly stops using their input during a visible grant and can reclaim it at any time.

## Menu items of Electron apps

Amended 2026-11-04 for issue #39, with the user's explicit approval. Electron passes `[NSApp currentEvent]` to a menu item's click handler and reports anything but a mouse click as the item's keyboard shortcut (`triggeredByAccelerator`). AppKit runs an accessibility press with no current event, so every AXPress on an Electron menu item arrives as a shortcut. Apps that drop shortcuts while a text field has focus ignore it. A mouse event posted before the press doesn't become the current event; only menu tracking makes one, and tracking follows the real pointer. So a press on such an item can use the Input Queue.

- Scope: `press` on an enabled item of an Electron app's own menu bar, reached from a menu bar title. The Apple menu, context and pop-up menus, status items and other apps' menus keep accessibility. The press takes the queue by default only while the app's focused element takes text; `real_input: true` asks for it anyway and `real_input: false` sends the accessibility press, which arrives as the shortcut.
- The loan brings the agent's window forward as a drag's does. Then the Agent Display's own menu bar shows the app's menus: accessibility places the titles there. The pointer moves to the title on that display and waits up to a second for the screen to show that app's title there, which also covers a menu bar that hides until the pointer reaches it. Without one, as when Displays have separate Spaces is off, nothing is clicked. The menu the click opens must lie wholly on the Agent Display, or it closes and the loan stops. The pointer then reaches the item, across first into a submenu, and clicks it. A submenu counts as open only once its frame lies on the display: a closed one of Electron's reports a 10×10 frame at the main screen's bottom left.
- Before every event the loan checks the grant, the user's touch, secure input, the display's frame, the app still in front and the menu still open. On any stop, a menu the loan opened closes with AXCancel. No key is sent, Escape included.
- While a request for the item waits or runs, the item is not pressed through accessibility: it would run twice. A declined or lapsed request returns `input_pending` and nothing else happens. A result the call has read is cleared, so pressing the same item again is a new request.
- When the loan has run and the session has nothing else waiting, the session is done. When no other agent is using the approval, the grant then ends at once and the pointer and front app come back; otherwise it lasts until the others are done too or it idles out.

## Clicks

Amended 2026-11-06 for issue #134. Some apps take a click sent in the background only partway. WeCom selects a sidebar row on a posted click and never opens the conversation; a real click opens it. The events don't tell Agent Screen that a click had no effect, so it doesn't guess.

- Scope: `left_click`, `double_click` and `triple_click` on the `computer` tool, with held modifiers. `right_click`, `middle_click` and a left click with Control held, which macOS takes for a right click, are refused with `real_input` before anything is queued or sent. The menu or popover a real click opens belongs to the app the loan brought forward, and it closes as soon as the grant's end makes the user's app front again, so the agent would never see it and might ask the user again. Keeping it open would mean keeping the user's front app away until the agent's next call. A menu item's real click avoids this by choosing the item in the same loan. The error points to `act_on_element`'s `show_menu` and to pressing the menu bar item. A left click on a pop-up control has the same limit, and the tool's description says so. The agent clicks in the background first. Only when a screenshot or the window's tree shows the click had no effect does it repeat the click with `real_input: true`. A click without it never enters the queue.
- One request is the whole click, a double click's two presses included. It waits up to 60 seconds for approval, as a drag does. A declined or lapsed request returns `input_pending`, and nothing goes out on the background route either. The card and the notification name the click, its point on the display, the app and the window's title.
- At request time the point must lie inside the Agent Display and inside a window on it, and Agent Screen notes what lies there. Accessibility gives the element at the point, after asking a Chromium or Electron app to publish its page's elements: its role, subrole, title and description, and the name and frame of the row, cell or link it sits in, or else its own frame. The row's name is its first static text, depth first, that has a letter and isn't a time, date, count or day: what is left of "10:30 AM", 下午3:05, "2m", 3分钟前 or 11月8日 once numbers, separators and units go is nothing, a unit letter or a day word such as Yesterday, Mon or 昨天. A name with a number, such as 项目组2024, still counts; failing all, the row's title or description. The walk stops at the name, and during the loan the frame isn't read. The reads take at most 1 second when the agent asks and 300 ms during the loan, where the user's pointer waits; an app that stalls past that leaves the element unknown. The loan reads it only when the request named one. A native list's hit element is usually a static text or an image, whose own text, such as a message preview, isn't read: it changes with each new message. The request logs what it will compare. The pixels of that frame, cut to the window, are captured as the agent's screenshot shows them. When the frame is missing, doesn't hold the point, is taller than 200 points, as a whole pane is, or is under 8 points, a 300 by 64 point band around the point is captured instead. The region never spans the whole window, so a sidebar that reorders doesn't refuse a click in the pane beside it. Just before the window comes forward, the loan looks again at the same region and element. The element check is the main guard: it refuses when an attribute both reads returned differs. When both reads named the row, the hit element's title and description are left out, since a link spanning a web row carries the row's unread count and time there. The element check runs once more after the window has come forward, since under AeroSpace that can take a second. An app that times out names nothing, or leaves out an attribute; an unknown element on either side, or an attribute only one read returned, leaves the decision to the pixels. They refuse when more than 10% of the region's samples moved by more than 32 of 255 in a color channel, as when a new message reorders a chat list under the point, and the log line gives the percentage. A blinking caret, a hover tint or a new time stamp in the same row stays under that limit (`real_click::looks_same`): a false refusal after the user allowed the click costs more than a rare missed reorder. Either refusal clicks nothing and tells the agent to take a new screenshot and ask again. When the same click is refused that way twice in a row, the area keeps changing, as a video does, and the agent is told to use `act_on_element` or `request_help` instead. A click that ran reports how long its request waited. The loan brings that window forward as a drag's does, moves the pointer to the point, and presses and releases there, each press released before the next. Click states count up from 1 within the request, so the app reads a double click as one. Before every event the loan checks the grant, the user's touch, secure input, Takeover, the display's frame, the window's frame, that the window is still the one under the point, and that its app is in front. A stop releases every button the loan pressed.
- As with menu items, when the loan has run and the session has nothing else waiting, the session is done. When no other agent is using the approval, the grant then ends at once and the pointer and front app come back, as soon as it ends, not at the queue's next once-a-second check. The front app's main window and its focused window, saved at grant start, are made main and focused again before the app comes back, the main one first, since a focused panel can't become main, so the user's typing goes to their window even when the loan's window belongs to the same app, as a second Chrome window does. A result the call has read is cleared, so the same click made again is a new request.
