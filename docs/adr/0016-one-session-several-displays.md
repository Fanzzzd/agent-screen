# One Agent Session can use several Agent Displays

A session used to have at most one Agent Display, and a repeated `create_display` returned it (ADR 0002). Some tasks need two screens at once, such as two apps that each need a full display, and an agent with one display had to keep swapping windows on it. So one session can now use up to four live displays.

`create_display` still returns the session's display by default. Most agents need one screen, and each new virtual display makes WindowServer and ColorSync reconfigure every screen; dozens in a few hours once froze a Mac. A new parameter, `new: true`, makes another display for the session, with its own title and Display Label. A session may have four live displays. A fifth `new` call fails, names the four handles, and tells the agent to end one first. A Review Display doesn't count, as the session no longer uses it. Without `new`, a session with several displays gets its latest one back, and the reply lists every handle it has. Two displays of one session never share a title: a repeated title gets a number, so Peek and the menu tell them apart.

Every tool already takes a display handle (ADR 0002), so a call with the handle of the session's other display acts on that display. There is no default display: `display_id` is required, so an agent with two displays can't act on the wrong one by leaving it out.

The model has an Agent Session now (`crates/model/src/session.rs`). It holds the session's live displays, in the order it made them, and its Window Authorization. ADR 0013 already said the authorization belongs to the session. It covers all the session's displays. A window the user took back on one display stays out of it on the other. It ends when the session's last live display ends, or when its connection closes, which ends every display of the session and clears the authorization once. A Takeover is per display: it pauses Placements under the authorization onto that display, while the session's other displays go on. Each display keeps its own records, Takeover, Agent Pointer, Review state, Recording and Help, Control and Window Requests. The apps a session started stay recorded on the display they were started for, since that display's catch decides where their new windows go. Taking a window back from any of the session's displays makes its app the user's on all of them.

A window on the session's own other display is the session's. place_window moves it from there as a Placement, with no Window Request, and the window keeps its record: a Handover stays a Handover and still goes home when its new display ends. A not-found message never blames "another agent session" for the session's own display. The stray filter counts the session's own records, so a window an app opened on the user's screen is a stray of whichever of the session's displays asks. place_window refuses to take a window from a display of the session that the user is operating.

`end_display` ends one display. Its handle stops working, and the session's other displays go on. `Core::end` and `Core::connection_closed` used to repeat the platform side of a display ending, and they had drifted apart: one told the Input Queue the display ended, the other didn't. Both now run one step for each display the model reports ended.

The Input Queue's participants stay per display, but a session declares itself done for all its displays at once. CONTEXT.md says the Input Grant ends when every participating session is done, and a session that said done on one display would otherwise keep the grant open through its other.

After the app restarts, `create_display` adopts the apps the session started on an earlier connection, so their windows, which macOS moved to the user's screen, are strays again. The MCP server used to hand every such app to the next display created by any session it served, and Codex serves several sessions from one process. An agent saw a window of an app it launched earlier pulled onto another agent's display. Now the MCP server keeps each display's session key, and `create_display` adopts only the asking session's apps. Each goes to the display it was on if the app gave that display's id to one of the session's displays again, and to the display the call made or reused otherwise.
